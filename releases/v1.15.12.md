# v1.15.12 — trees no longer float above the grass (F10)

**Cosmetic.** One bug class (world-gen pixel-perfectness), one round, one file.
A one-pixel air gap at every tree's base read as the trunk hovering above
the grass. The trunk loop's stop-condition was `wy < t.s`, which left the
surface row untouched; the surface row was always grass via an early-return.
The fix extends the trunk to `wy <= t.s` so it can overdraw the grass pixel
at the trunk's 2-px column. Canopy ellipse is unchanged (it covers the
topmost trunk rows by design and had no matching gap).

## Summary

- **Verdict:** Cosmetic. No behaviour change, no gameplay-rule change, no
  physics or survival change. The world is rendered correctly.
- **Scope:** `scripts/lua/rpg.lua` only. No plugin changes, no native
  rebuild.
- **Behaviour delta:** every tree generated by `gen()` now has its trunk
  visually flush with the grass surface. Before this fix, every tree had a
  1-px air gap at the base that read as the trunk hovering.
- **Risk:** zero gameplay risk. The change is `wy < t.s` → `wy <= t.s`
  in the trunk loop plus hoisting the trunk check out of the
  `wy < surf` block; the only pixel ever touched is the grass pixel at
  the trunk's 2-px column, which the trunk was always supposed to
  overdraw. No other element is touched.

## Changes

Bullet pulled verbatim from `R.CHANGELOG[1]` at `scripts/lua/rpg.lua:203-205`:

- F10: trees no longer float above the grass. The trunk loop at `genBase`
  stopped drawing WOOD one pixel short of the surface row (`wy < t.s`) and
  the surface row itself was always `b.grass` via an early-return, leaving
  a 1-pixel air gap that read as the trunk hovering. Extended the trunk to
  `wy <= t.s` and hoisted the trunk check out of the `wy < surf` block so
  it can fire at `wy == surf` and overdraw the grass pixel at the trunk's
  2px column (Terraria/Minecraft-style). Canopy ellipse unchanged — it
  has no matching gap (covers the topmost trunk rows by design).

## Affected files

- `scripts/lua/rpg.lua` — sole change.
  - `genBase`'s trunk loop condition changed from `wy < t.s` to
    `wy <= t.s`. The loop body draws a 2-px-wide WOOD column at each row;
    extending the loop by one iteration lets the trunk reach into the
    surface row.
  - The trunk check is hoisted out of the `wy < surf` block so it can
    fire at `wy == surf`. Previously, the trunk was drawn inside the
    `wy < surf` block and the surface row itself was always grass via
    an early-return, leaving a 1-px gap regardless of how many trunk
    iterations ran.
  - Canopy ellipse is unchanged (same `gen()` site, different block). The
    canopy covers the topmost trunk rows by design — it has no matching
    1-px gap and would not benefit from being extended.
  - No other change anywhere in the file. No new fields, no new helpers,
    no `R.VERSION`-adjacent code, no `R.CHANGELOG` mutation outside this
    single new entry.

## Migration notes

- **No plugin changes required.** World-gen runs entirely inside
  `rpg.lua`'s `gen()` path; plugins consume the generated world but do
  not influence tree placement. The fix is a per-pixel rendering change
  only.
- **No save-format changes.** Existing saves are unaffected. The fix
  applies only on **new world generation** (next time `gen()` runs to
  place trees); already-generated worlds keep their trees as they are.
  This is intentional — re-generating trees on existing saves would be a
  separate, far riskier change.
- **No HUD / UI changes.** Pure world-rendering change. The always-on
  HUD (`Deaths: N`, version readout), inventory panel, crafting panel,
  and Esc/Options menu are all unchanged.
- **For plugin authors:** if any plugin wraps or extends tree generation
  (none currently do), the canonical tree placement site is the trunk
  loop inside `genBase` in `rpg.lua`. Future tree-related changes should
  land there or in a sibling helper inside the same `gen()` site.

## How-to-verify

The lab instance has `worldEverGen = false` by design, so visual
verification of a generated tree is not possible on the lab. **The
following procedure runs against the user's live session**, not the lab.
This is explicit in Main's brief and is the only way to confirm the
fix visually.

1. **Pre-flight.** Confirm the always-on HUD top-right version readout
   reads `v1.15.12` (or newer). If it reads `v1.15.11` or earlier,
   reload rpg.lua first or wait for the next restart — the change has
   not taken effect on your build yet.
2. **Start a new world.** From the title screen, click **Play** →
   **New World** (or **New Seed** if you want a different seed to make
   the trees easier to find). Do NOT verify against an existing save —
   the fix applies only on new world generation; already-generated trees
   retain their original (gap-floating) pixels.
3. **Find a tree.** Walk in any direction until a tree is visible on
   screen. Trees are the 2-px-wide WOOD columns with a green canopy
   ellipse on top, generated by `genBase` / `gen()`. With a fresh seed
   you'll typically see one within ~10 seconds of walking.
4. **Path 1 — look at the trunk base.** Crouch or step back so the base
   of the trunk is visible at a comfortable angle. Inspect the row where
   the trunk meets the grass. Expected: the trunk's 2-px WOOD column
   touches the grass surface directly. There is **no visible air gap**
   between the bottom of the trunk and the grass below it. The trunk
   reads as rooted in the ground, not floating. Before this fix, you
   would see a single-row gap of grass-with-no-trunk-pixel between the
   trunk's bottom and the grass surface — that gap is the bug.
5. **Path 2 — compare against the canopy.** Look at the top of the same
   tree, where the canopy ellipse meets the topmost trunk rows. Expected:
   the canopy still overlaps the topmost trunk rows normally (canopy
   has no gap, by design — it intentionally covers the topmost trunk
   rows so the trunk-to-canopy transition reads as smooth). The fact that
   the base is now gap-free while the top remains gap-free by design is
   the correct post-fix state; if either side shows a gap, that's a
   regression.
6. **Path 3 — generate several worlds, check several trees per world.**
   Click **Quit to Menu** → **Play** → **New Seed** a few times. Each
   new world should generate trees with the same gap-free base. If only
   some trees are gap-free, that's a regression — the fix is in
   `genBase`'s loop, which runs for every tree in every world, so any
   gap-free tree implies all trees should be gap-free.
7. **Negative test — existing-save trees unchanged.** Open an existing
   save (from before this build). Walk to a known tree location. Expected:
   the trunk **still has the 1-px air gap** at its base. This is
   intentional — the fix applies only on new world generation, not
   retroactively to already-generated worlds. If an existing-save tree
   is gap-free, that's not a regression but it does mean either the
   save was generated post-fix or some other code path re-ran tree
   generation, which is worth a separate bug report.
8. **Negative test — non-tree surface pixels unaffected.** Walk away
   from the tree and look at any non-tree grass tile. Expected: the
   grass surface renders identically to before — same colour, same
   pixel-perfectness. The fix only touches the trunk's 2-px column on
   the surface row; every other grass pixel is untouched. If the grass
   surface looks visually different from before, that's a regression —
   the change should be invisible except where the trunk meets the
   grass.
9. **Cross-version regression check — companion + bed respawn.** The
   v1.15.7 / v1.15.9 / v1.15.10 respawn-path fix cluster is unrelated
   to world-gen, but worth a quick smoke test: place a bed (if you're
   on the survival.lua path), die to a known cause, and confirm
   companion teleports to the new spawn + overhead region clears + stats
   reset. This should be unchanged from v1.15.11 — no regression
   introduced by the world-gen tweak.
10. **Architecture verification — trunk loop condition is `wy <= t.s`,
    not `wy < t.s`.** Open `scripts/lua/rpg.lua` and search for
    `wy <= t.s` inside `genBase`. Expected: at least one hit inside the
    trunk loop, and the trunk-check code now runs at `wy == surf` (not
    gated by `wy < surf`). If the loop still reads `wy < t.s`, the round
    is incomplete.
