# Release v1.15.8 — companion.lua's queued-chain replay + chatQueue-leak fixes (+ version-bump convention)

## Summary

Three things in v1.15.8:

1. **A forward convention note** — rpg.lua owns `R.VERSION`; every plugin fix from now on
   rolls into the next rpg.lua version bump with its own CHANGELOG entry (so users see one
   unified version-by-version stream rather than per-plugin drift).
2. **F2 (companion.lua)** — `R.companionKill()` now also clears `C.queue`. Before this, a
   queued action chain survived the death / revive cycle and each step replayed
   step-by-step on revival, calling chain-fail-cleanup behavior that didn't match player
   intent after a forced test kill.
3. **F3 (companion.lua)** — `R.hooks.newworld` now resets 7 additional `R.COMP` fields
   the original reset missed: `C.x`, `C.y`, `C.vx`, `C.vy`, `C.chatQueue`, `C.sayMsg`,
   `C.sayAt`. Fixes a one-frame ghost at the previous world's last position and the
   chatQueue leak where driver messages queued in the previous world drained into the
   next one.

## Changes

- **CONVENTION (going forward)** — `rpg.lua` owns `R.VERSION`; ALL plugin fixes roll into
  the next `rpg.lua` version bump with their own CHANGELOG entries (one unified
  user-visible stream, matches `@github`'s `CHANGELOG.md` practice). Practically: if a
  plugin has shipped a fix, the next `rpg.lua` bump carries it as a sub-entry with its
  own `F#` tag (e.g. "F2 (companion.lua)") rather than a separate per-plugin version.
- **F2 (companion.lua)** — `R.companionKill()` now also clears `C.queue`. Before, a
  queued chain survived the death / revive cycle and each step replayed step-by-step,
  calling into chain-fail-cleanup behavior that didn't match player intent on a forced
  test kill.
- **F3 (companion.lua)** — `R.hooks.newworld` now resets 7 additional `R.COMP` fields
  that the original reset missed: `C.x = 0`, `C.y = 0`, `C.vx = 0`, `C.vy = 0`,
  `C.chatQueue = {}`, `C.sayMsg = nil`, `C.sayAt = nil`. Fixes a one-frame ghost at the
  previous world's last position and a chatQueue leak where driver messages queued in
  the previous world would drain into the next one.

## Affected files

**This is the first release in the `releases/` folder that touches both rpg.lua AND a
plugin** — worth flagging because every prior release notes page so far has been a
single-file change. From the convention note in this same round, this pattern is now the
expected default rather than a one-off:

- `scripts/lua/rpg.lua` — `R.VERSION` bumped to `1.15.8`; three new `R.CHANGELOG` notes
  inserted (CONVENTION, F2, F3 -- verbatim copy of the companion.lua change summaries so
  the in-game `/r` changelog screen reads the same as this release page).
- `scripts/lua/rpg_plugins/companion.lua` — F2: extended `R.companionKill()` with a
  `C.queue = {}` reset (so the queue doesn't survive the kill → revive cycle). F3:
  extended the `R.hooks.newworld` callback registered in this file with the seven
  additional `R.COMP` field resets (position, velocity, chat queue, current say
  message + timer).
- `scripts/lua/rpg_plugins/survival.lua` — **not touched** at v1.15.8 time (Batch C
  bed-respawn pollution bypass is still pending per the hub log).

## Migration notes

None for F2 / F3 themselves — they're internal-state corrections, no signature change,
no save-format change, no behavior change for any caller beyond the two specific bugs.
The **CONVENTION note** is the only thing a downstream reader needs to be aware of: from
v1.15.8 onward, plugin fixes land in the next `rpg.lua` version bump rather than as their
own per-plugin version. Anyone tracking releases by version number should expect fewer
total version bumps (good: one stream not three) and slightly fuller single-version
release pages (real consequence of the convention; called out explicitly in the
`Affected files` section above).

## How to verify

**F1-of-this-round verification — driving the entry-level confirmations are easy; the
real diff is whether the queue gets drained post-revive:**

1. Build or update to v1.15.8.
2. From the chat / debug console (or a scripted test), queue a chain of companion actions:
   something like "queue 2 commands into `C.queue`, then call `R.companionKill()`."
3. Revive the companion (auto-respawn via `REVIVE_DELAY`, or force one).
4. Before this fix: each queued step replays in order, even though the player intended to
   wipe the queue when they killed the companion. After this fix: the queue is empty
   post-kill; revival comes up with a clean slate and the player has to re-issue any
   commands they actually wanted.

**F3 verification (one-frame ghost + chatQueue leak):**

1. Build or update to v1.15.8.
2. World A — run a session for a bit, queue a few messages on the companion's
   chatQueue (`R.COMP.chatQueue` should grow non-empty over time when the player is
   talking), confirm her position is something non-origin.
3. Generate World B (Esc → New World, or the same path the engine's newworld hook
   fires on).
4. Before this fix: one frame at the moment of the world-switch, the companion ghost
   appears at World A's last position (a 1-frame artifact), and any chatQueue messages
   queued in World A drain in World B (driver messages from the previous session
   showing up in the new one). After this fix: clean snap to origin with no ghost, and
   `R.COMP.chatQueue` reads `{}` after the hook fires.

**Convention verification (meta-level):**

1. Look at the next plugin-only fix that ships.
2. Confirm `R.CHANGELOG` reads that fix as a sub-entry of the next `rpg.lua` version
   bump rather than a separate per-plugin bump.
3. Confirm the in-game `/r` changelog dialog and `D:/The-Powder-Toy/CHANGELOG.md`
   both gain the same entry (so users and devs see the same single stream).
